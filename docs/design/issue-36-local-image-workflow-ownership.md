# Issue #36 本地图片工作流所有权与图床接力

> 状态：已确认
> 关联 Issue：[Issue #36](https://github.com/ytahml/obsidian-image-manager/issues/36)

## 背景

当前插件会拦截粘贴和拖放，自行创建、命名、移动本地图片并插入引用，还可能立即开始自动上传。其他附件管理插件可能随后通过 Vault 事件移动或重命名同一文件并更新同一引用，双方在附件尚未稳定时竞争，可能造成远程路径使用旧文件名、引用替换错位、批量修复风暴或误判孤立图片。

Attachment Management 是首个真实兼容基线，但不是运行时依赖。

用户无法提供稳定复现 Issue #36 中某个具体故障的操作路径。因此本需求不定性为问题修复，也不以“原问题不再复现”作为完成依据；它是对本地图片生命周期的职责拆分、状态协调和第三方附件管理兼容性优化。

### Attachment Management 固定基线事实

核查版本：`363c9d63a2a66867b774cfee0dac51c60d07e44e`（0.12.1）。

- `vault create` 只把新附件加入 FIFO 队列；后续 `vault modify` 发现队首附件引用后才启动异步本地处理。[事件链](https://github.com/trganda/obsidian-attachment-management/blob/363c9d63a2a66867b774cfee0dac51c60d07e44e/src/main.ts#L58-L118)
- rename 完成后才更新来源引用，但插件没有向其他插件暴露事务 ID、完成事件、回调或可等待 Promise。[创建与引用更新](https://github.com/trganda/obsidian-attachment-management/blob/363c9d63a2a66867b774cfee0dac51c60d07e44e/src/create.ts#L58-L191)
- 代码中的 `1000 ms` 是 create 新鲜度过滤阈值；`500 ms` debounce 只合并 rename Notice，均不是附件处理稳定期。[create 过滤](https://github.com/trganda/obsidian-attachment-management/blob/363c9d63a2a66867b774cfee0dac51c60d07e44e/src/main.ts#L58-L84) [Notice debounce](https://github.com/trganda/obsidian-attachment-management/blob/363c9d63a2a66867b774cfee0dac51c60d07e44e/src/create.ts#L14-L39)
- README 只说明后处理显示会延迟，没有给出固定完成时长。[Known issues](https://github.com/trganda/obsidian-attachment-management/blob/363c9d63a2a66867b774cfee0dac51c60d07e44e/README.md#L142-L147)

因此，通用协作不能把第三方代码中的任何固定毫秒值当作完成信号；只能依据公开状态求解可接力资格，并由本插件提供防抢跑保护与硬超时。

## 目标

- 优化图片从粘贴/拖放、附件创建与外部整理，到图床接力、引用替换和可选本地回收的完整生命周期。
- 允许用户把本地图片管理权交给 Obsidian 或其他附件管理插件。
- 在不争夺本地管理权的前提下，保留粘贴后的自动图床接力。
- 使用通用协作机制兼容遵循 Obsidian 标准事件与引用行为的附件管理者。
- 通过 `delegated + autoUploadOnPaste=false` 为不需要任何粘贴/拖放集成的用户提供明确的完全关闭边界。

## 非目标

- 不声称已经复现或修复某个确定的 Issue #36 缺陷。
- 不依赖 Attachment Management 的插件 ID、内部队列、延迟常量或私有实现。
- 不从单一第三方插件的当前行为推导所有附件管理插件都必须遵守的协议。
- 不在本需求中改变或诊断现有图片压缩的编码格式与文件扩展名策略。
- 不在设计草案确认前开始实现。

## 领域语言

- **本地管理权**：谁负责新附件的本地创建、命名、路径、内容处理和初始引用更新。
- **本地管理模式**：本地管理权归本插件的 `managed`，或归 Obsidian/其他附件管理者的 `delegated`。
- **粘贴后自动上传**：独立于本地管理模式的自动化选择。
- **自动图床接力**：本插件在其他管理者处理后的附件达到可接力状态时执行上传和精确引用替换。
- **通用协作**：只依据 Obsidian 公开事件和最终可解析状态进行协作。
- **附件管理者**：拥有当前新附件本地管理权的 Obsidian 或插件。
- **可接力状态**：候选文件、目标引用及唯一映射在当前均可验证，但不声称第三方未来不再修改。
- **事务影响**：变更是否影响候选文件、目标引用或两者的唯一映射，不区分行为来源。
- **状态未定图片**：仍处于委托事务或近期外部变更保护中，不能根据当前扫描声明为孤立的本地图片。
- **强收敛**：已观察到文件移动或重命名，随后目标引用跟随更新并唯一解析到最新文件。
- **弱收敛**：文件与初始引用已唯一映射，但尚未观察到后续文件变化与引用跟随证据。

## 已确认的产品决策

### D1：产品承诺

用户可以把本地图片的创建、命名、移动和引用更新完全交给 Obsidian 或其他附件管理插件，同时继续使用本插件的粘贴后自动上传、远程引用替换和图床管理能力。

因此，委托模式不是简单关闭粘贴功能，而是让渡本地管理权并保留自动图床接力。

### D2：兼容范围

兼容机制采用通用协作：只观察 Obsidian 公开事件和最终可解析引用，不依赖特定插件的 ID、内部队列或固定延迟。Attachment Management 作为首个真实验收对象。

### D3：本地管理权与自动上传正交

不采用 `managed / delegated / off` 三态模型。设置拆成两个独立决策：

- 本地管理模式：`managed / delegated`。
- 粘贴后自动上传：`on / off`。

`delegated + off` 表示不接管本地附件，也不执行粘贴后自动图床接力，不需要额外的 `off` 模式。手动上传、图片浏览器和远程管理不由自动上传开关关闭。

### D4：本地管理模式只约束自动粘贴与拖放流程

`managed / delegated` 控制自动发生的粘贴和拖放处理，不直接关闭用户主动执行的本地重命名、整理等命令。用户显式操作与自动争夺本地管理权是不同边界；这些命令按 D10 提供与风险相称的提示。

### D5：关闭自动上传时不建立委托事务

`delegated + autoUploadOnPaste=false` 不建立粘贴事务、不收集候选文件，也不启动收敛缓冲计时器。此承诺只针对粘贴/拖放事务；图片浏览、远程引用索引失效等既有功能所需的 Vault 事件不受影响。

### D6：旧配置保持原行为

新增的本地管理模式对新安装和旧配置均默认 `managed`。只有用户主动选择 `delegated` 后才让渡本地管理权，升级本身不得改变粘贴、命名、路径、压缩或自动上传的**有效行为**。

旧实现使用 `autoUploadOnPaste && reorganizeConvertFormat` 作为自动上传条件。迁移时新自动上传值按旧条件计算：

```text
newAutoUploadOnPaste =
  oldAutoUploadOnPaste
  && oldReorganizeConvertFormat
  && canResolveEnabledHosting
```

因此旧数据虽然保存 `autoUploadOnPaste=true`，但因 Markdown/hosting 门控而实际关闭，或没有可解析的启用图床时，迁移后会明确保存为关闭，避免解除旧门控后突然产生网络上传或每次进入必然失败的流程。迁移只验证本地配置能否解析目标，不发起连接测试或验证凭据。

### D7：按事务影响判断可接力状态

委托自动接力不要求用户停止编辑，也不区分变更来自用户、Obsidian 还是其他插件。协调器只判断变更是否影响本次事务的候选文件、目标引用及两者的唯一映射：

- 无关编辑不阻塞接力。
- 相关变化使事务重新求解。
- 目标引用被删除时取消对应自动接力。
- 无法唯一恢复候选文件与目标引用的映射时失败关闭。

可接力状态是当前可验证的保守接力资格，不宣称已经识别第三方插件真正的最终完成时刻。连续粘贴应形成彼此隔离的事务并按后续决策协调。

### D8：一个粘贴事务包含独立图片项

一次粘贴或拖放建立一个事务，每张输入图片形成独立项目。每项必须唯一建立“输入图片—最终 `TFile`—本次新增引用”的映射；某项歧义、取消或失败不阻塞其他已经确定的项目。操作结束后汇总成功、取消和失败数量。

### D9：委托自动上传只压缩上传副本

`delegated` 下本插件不得修改附件管理者创建的本地图片内容。启用 `compressBeforeUpload` 时只能压缩内存中的上传载荷；Vault 中的最终 `TFile` 保持不变。`managed` 继续通过 `compressManagedPasteLocal` 保留粘贴创建前处理本地内容的现有能力。

### D10：显式本地修改保留，但按风险提示

`delegated` 不禁用用户主动执行的本地修改能力：

- 重命名界面提示外部附件管理器可能再次重命名或移动。
- 整理确认提示外部策略可能撤销批量路径调整。
- 覆盖本地文件的显式压缩在执行前确认内容哈希和外部管理关联风险。
- 只处理上传副本的压缩不提示本地修改风险。

### D11：外部 rename 修复从固定延迟改为保守协调

- 委托粘贴事务内的 rename 先抑制自动引用修复，等待附件管理者更新引用。
- 达到可接力状态且引用可解析时不修复。
- 保护阶段后仍存在确实无法解析的旧引用时才尝试保守修复。
- 连续 rename 合并处理，避免每次触发全 Vault 扫描。
- 引用有效性使用 Obsidian 链接解析语义，不按 basename 猜测。
- 非粘贴事务的外部 rename 仍保留修复能力，但同样批处理并准确解析，以保留 Obsidian 内部链接自动更新关闭时的历史保护。

### D12：委托活动期间不得声明孤立

属于活跃委托事务或近期外部移动、重命名、引用更新保护范围的图片标记为状态未定，不得显示为可删除孤立图片，也不得进入实际回收流程。事务结束或最后一次相关变化后，对受影响图片保留 `2 s` 保护；相关变化重启该图片的保护期。保护不阻塞其他图片或整个扫描，结束后仍执行展示扫描、确认前复扫和执行前复扫。

### D13：事务绑定来源笔记，不绑定活动编辑器

- 切换活动笔记不迁移或取消原事务。
- 原 Editor 仍存在且有未保存内容时，以该 Editor 当前内容验证。
- 原 Editor 关闭后，只有 Vault 中已保存内容能唯一恢复目标引用时才继续，否则取消。
- 来源笔记或候选附件删除时取消对应项目。
- 插件卸载时取消全部未完成事务，不继续上传或写入。
- 插件重新加载后不恢复旧的内存事务。

### D14：只替换事务引用并保守回收本地文件

- delegated 自动接力只替换本次事务中已验证的精确引用，不扫描扩大到其他位置或其他笔记的同文件引用。
- `keepLocalCopy=false` 时重新扫描整个 Vault；只有确认不存在任何本地引用且替换后事务指纹仍有效，才通过回收站删除本地文件。
- 扫描失败、状态歧义、存在其他引用或事务变化时保留本地文件。
- 上传后验证失败时不修改引用、不删除本地文件；远端可能留下未引用对象，向用户报告但不自动删除。

### D15：自适应防抢跑与硬超时

- 强收敛采用 `200 ms` 防抢跑缓冲。
- 弱收敛采用 `800 ms` 防抢跑缓冲。
- 只有影响候选文件、目标引用或唯一映射的变化才重新求解并重启对应缓冲；无关编辑不重置。
- 从粘贴/拖放事件开始采用不可延长的 `30 s` 硬超时。
- 超时失败关闭，保留本地文件和引用并提示用户稍后手动上传。
- 三个时长首版为内部可测试常量，不暴露用户设置；真实 Obsidian 验收若提供反例，再基于证据调整。

### D16：拆分粘贴引用格式、整理转换与图床门控

- 新增 `managedPasteReferenceFormat: markdown | wiki`，只控制 managed 粘贴生成的本地引用。
- `reorganizeConvertFormat` 只控制显式整理是否转换为 Markdown。
- 图床配置、手动上传和自动上传不再受上述两个设置门控。
- delegated 忽略 `managedPasteReferenceFormat`，初始引用由附件管理者决定。
- delegated 可接收 Wiki 或 Markdown 本地引用；接力后将事务精确引用替换为标准远程 Markdown 或有效自定义引用模板。
- 旧配置按 `oldReorganizeConvertFormat ? markdown : wiki` 迁移 `managedPasteReferenceFormat`，并原样保留 `reorganizeConvertFormat` 的整理行为。

### D17：上传期间事务变化时不自动二次上传

- 发出上传请求前发生相关变化时返回求解阶段，仍受原硬超时约束。
- 每次网络重试前重验事务指纹，失效即停止重试。
- 请求发出后发生变化时允许在途请求结束，但结果不可用于引用替换或本地删除。
- 不因事务状态变化自动上传新状态，也不自动删除已上传但未采用的远端对象；向用户汇总报告并要求手动重试。

### D18：并行观察、有限上传、串行写入

- 每个 paste/drop 事件建立独立事务；同一来源笔记可同时跟踪多个事务。
- 引用重定位、替换和本地回收等同笔记写操作串行执行。
- 已达到可接力状态的图片最多两项并发上传，每项上传前后重验自身指纹。
- 不按内容哈希、basename 或事件临近性强行配对相同字节、名称或引用；只能依据事务差异、`TFile` 身份和唯一引用映射。
- 无法唯一归属时只跳过歧义项，不影响其他事务。

### D19：拆分本地粘贴压缩与上传载荷压缩

- `compressManagedPasteLocal` 只在 managed 粘贴/拖放时修改新建本地附件。
- `compressBeforeUpload` 用于自动上传、当前图片上传、笔记上传和批量上传，只处理上传载荷。
- 两者共享 `compressQuality`；显式“压缩当前图片”命令保持独立。
- delegated 不启用本地粘贴压缩，但可继续压缩上传载荷。
- 旧 `autoCompress` 同时迁移给两个新设置，以保持 managed 用户原行为。
- managed 自动上传时，已经按相同质量压缩的本地结果直接作为上传载荷，避免重复有损压缩。

### D20：自动接力按事务汇总通知

- 每个 paste/drop 事务最多显示一次最终汇总，不为内部事件、重验或状态变化逐项弹 Notice。
- 全部成功时沿用简短成功提示；用户主动删除目标引用导致取消时静默处理。
- 部分成功、歧义、超时、上传失败或上传结果失效时，显示一次成功/取消/失败数量和首个安全原因。
- 上传完成但结果未采用时，明确说明引用未替换、本地文件已保留、远端可能存在未引用对象。
- 不显示响应正文、签名 URL、凭据或敏感 query；不提供自动重试按钮，提示使用显式上传命令。

### D21：设置页分离本地管理与图床接力

- 设置页分为“本地附件管理”和“图床接力”。
- delegated 下保留但禁用路径、命名、命名提示、managed 粘贴引用格式和本地粘贴压缩，并解释本地附件由其他管理者负责。
- managed 与 delegated 均显示自动上传、上传载荷压缩、默认图床和引用模板；本地副本设置只在自动上传开启时显示或启用。
- 没有可用默认图床时不能开启自动上传，并引导先完成配置。
- Obsidian 1.13 声明式设置保持既定顺序、门控和说明；不再提供 1.12 imperative fallback。

### D22：在途事务使用配置快照且不静默换目的地

- 事务记录默认图床、压缩策略、引用模板和本地副本策略。
- 关闭自动上传或从 delegated 切回 managed 时，取消尚未发出上传请求的 delegated 事务。
- 切换到 delegated 只影响之后的新粘贴，不追溯已有附件。
- 快照图床被切换、禁用或删除时，已有事务不得改投其他图床；上传前验证失败则取消。
- 在途网络结果仍按事务指纹重验；设置变化后不得继续替换或删除。
- 设置变化不追溯重处理已结束事务。

### D23：首期自动接力范围限于 Markdown 编辑器

- delegated 自动接力首期只承诺 Markdown 笔记编辑器。
- 桌面覆盖 paste 和 drop。
- 移动端仅在 Obsidian 提供同等 editor event、文件数据和 Provider 能力时支持 paste，不承诺拖放。
- Canvas 不纳入首期自动接力；其中的图片仍可使用显式上传能力。
- 未来只有在 Canvas 提供可靠公开 API 后才单独设计，不复用来源猜测逻辑。

### D24：需求定性为生命周期协作增强

Issue #36 有明确产品价值，但没有由用户掌握的稳定复现操作。本需求定性为本地图片生命周期和第三方插件兼容性优化，不是对已复现问题的 bug fix。完成标准必须依赖明确场景、竞争条件测试和真实兼容验收，不能表述为“原问题不再复现”。

## 设计树状态

产品目标、模式、事务、安全、迁移、交互、平台范围、验收和对外表述的决策前沿已走完，用户已确认共同理解。当前功能代码、自动化竞争测试和一组真实桌面受影响场景已经验证；完整真实矩阵仍未覆盖，因此不标记 Issue 36 整体完成。证据见 `docs/testing/issue-36-desktop-acceptance.md`。

## 用户流程与交互

### managed

本插件继续拦截 Markdown 编辑器 paste/drop，负责本地命名、路径、可选本地压缩和初始引用。自动上传关闭时流程在本地引用完成后结束；开启时使用事务配置执行上传、引用替换和可选本地回收。

### delegated

本插件不阻止 Obsidian 默认行为，也不创建、命名、移动或修改本地附件。自动上传关闭时不建立粘贴事务；开启时观察本次事件产生的候选文件和新增引用，按事务影响求解强/弱收敛，验证后接续上传并只替换事务精确引用。

### 显式操作

手动上传、笔记/批量上传、图片浏览器和远程管理在两个模式均可用。显式本地重命名、整理和覆盖压缩也保留，但 delegated 下显示对应外部策略或内容关联风险。

## 功能边界

- `managed / delegated` 只决定自动 paste/drop 的本地管理权；自动上传是独立开关。
- delegated 首期只支持 Markdown 编辑器；Canvas 自动接力不在范围内。
- 自动接力面向公开 Obsidian 状态，不承诺适配任意插件私有行为。
- 自动替换不扩展到事务之外的同文件引用。
- `keepLocalCopy=false` 不是删除授权捷径；仍需全 Vault 无本地引用和事务重验。
- 现有图片压缩编码格式与扩展名策略不在本需求中改变或定性。

## 技术设计

按依赖分为设置迁移、生命周期协调、委托事务、安全联动和验收五层。`main.ts` 只注册事件和编排服务；事务求解、可接力状态、时钟、串行写入与近期变更保护进入可独立测试的生命周期协调模块。

首期使用内存事务，不跨插件卸载恢复。协调器以 paste/drop 事件为事务边界，以输入图片为事务项，以来源笔记为写入串行化边界；上传最多两项并发。

## 安全、隐私与性能

- 所有歧义、超时、配置漂移和上传期间状态变化均失败关闭。
- delegated 不修改附件管理者创建的本地图片内容；上传压缩只处理内存载荷。
- 自动替换只触及事务精确引用；全 Vault 确认无本地引用后才允许回收。
- 活跃事务和近期外部变更图片为状态未定，不得声明或删除为孤立。
- 通知和错误不包含响应正文、签名 URL、凭据或敏感 query。
- 无关编辑不触发等待重置；相关事件驱动重求解，不轮询整篇笔记。
- 外部 rename 合并处理，避免每次启动重叠的全 Vault 扫描。
