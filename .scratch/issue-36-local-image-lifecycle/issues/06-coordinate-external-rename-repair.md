# 06 — 协调外部 rename 修复与显式本地修改

**What to build:** 在外部附件管理者移动或重命名图片时，Image Manager 不再固定延迟后与其竞争全库引用写入；同时保留关闭 Obsidian 内部链接自动更新时所需的保守断链修复，并向 delegated 用户解释主动本地修改风险。

**Blocked by:** 05 — 支持连续操作、多图与上传竞态的失败关闭。

**Status:** ready-for-agent

- [ ] 委托事务内的图片 rename 会抑制或延后自动引用修复，直到事务重新求解。
- [ ] 最终引用能通过 Obsidian 语义解析到最新 `TFile` 时不执行修复。
- [ ] 保护后仍存在确实断开的旧引用时才执行保守、准确的修复，不按新 basename 猜测候选。
- [ ] 非事务外部 rename 仍保留修复能力，以覆盖内部链接自动更新关闭的场景。
- [ ] 连续 rename 被批处理或防抖，不为每次事件启动重叠的全 Vault 扫描与写入。
- [ ] 本插件自己的重命名和整理不会与外部修复重复执行。
- [ ] delegated 的重命名界面说明外部策略可能再次移动或重命名。
- [ ] delegated 的整理确认说明外部策略可能撤销批量路径调整。
- [ ] delegated 的显式覆盖压缩在执行前说明内容哈希和外部管理关联风险；上传副本压缩不显示该警告。
- [ ] 测试覆盖事务内抑制、可解析 no-op、断链 fallback、连续 rename、内部链接自动更新开关和自有变更隔离。
- [ ] canonical 架构、本地工作流、设置/UI 与领域语言文档同步。
- [ ] `npm test`、`npm run build` 和 `git diff --check` 通过。
